# 2026-09-15

## Limite de anexo do Canvas: 3MB -> 25MB (arquivos) / 5MB (imagens)

- **Achado**: o teto de 3MB era 100% client-side, em
  `src/utils/file-validation.ts` (`MAX_FILE_SIZE` e `MAX_TOTAL_SIZE`).
  Nenhum limite no backend: `POST /api/file/upload` do agent-server streama em
  chunks de 8KB sem cap (`file_router.py::_upload_file`), e não há
  `LimitRequestBody` no Apache nem body limit em `ingress.mjs`/`static-server.mjs`.
  Testado ao vivo: 25MB -> HTTP 200 pela cadeia inteira (ingress :8092 e HTTPS
  do domínio de produção).
- **Por que dividir os tetos**: arquivos e imagens seguem caminhos diferentes.
  Arquivo comum vai por upload HTTP pro workspace (`uploadFilesToRuntime`).
  Imagem **não marcada** como "upload as file" é base64 no content block da
  mensagem -> vai pro LLM, inflando ~4/3. Por isso `MAX_IMAGE_SIZE` ficou em
  5MB e `MAX_FILE_SIZE`/`MAX_TOTAL_SIZE` em 25MB.
- As mensagens de erro agora derivam os números das constantes (`toMegabytes`);
  antes "3MB" estava hardcoded em 3 strings e mentiria após o bump.
- **Gotcha de teste**: `it.each` com objetos `File` nos args **derruba o Vitest**
  (`RangeError: Maximum call stack size exceeded`, falha na fase de coleta, 0
  testes; no pool `forks` aparece só como "Worker exited unexpectedly" — só com
  `--pool=threads` o erro real aparece). Solução: `it.each` só com escalares e
  construir o `File` dentro do corpo do teste.
- Para forjar tamanho sem alocar bytes: `new File([""], name, {type})` +
  `Object.defineProperty(file, "size", {value: n})`. Isso funciona normalmente.
- Deploy feito: `npm run build` aqui **é** o deploy (`build/` é servido pelo
  static-server na :3001 atrás do ingress :8092, atrás do Apache). Backup do
  `build/` antes, verificação do chunk novo, `rm -rf build.bak-*` depois.
  O chunk `llm-not-configured-banner-*.js` é onde esse código cai.
- **Pendente**: a mudança está em produção mas **não commitada**.
