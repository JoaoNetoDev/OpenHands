ACP provider switch on conversation error

The chat error banner gains a "Switch provider" recovery action. When an ACP conversation reaches any non-RUNNING state (error / stuck / limit-hit / paused / finished / idle / waiting-for-confirmation) the user can fork it into a fresh conversation against a different configured ACP agent profile, carrying over the source workspace, repository, branch, workspace mode, and plugins. The previous conversation stays intact; the user navigates straight into the new one.

1What & why

\u2605 Trigger broadened on purpose. The first draft gated the action on classification.kind \u2208 {rate_limit, quota}; in practice users hit the same need on internal, network, and stale-config failures. The shipped gate is ACP conversation && execution_status !== RUNNING. Re-auth remains its own button (ACPAuthRequired \u2192 settings/agents).

Three situations the new action resolves:

  • Provider limit hit. Claude Code reaches [-32603] monthly spend limit; the user continues with Codex or Gemini CLI on the same workspace.
  • Provider degraded. Internal / network error against one ACP CLI; the user hops to another without losing the repo / branch state.
  • Wrong model pick. The original conversation stays as a record; a fork with a different ACP provider / model preserves the prior turn history.

Implementation lands entirely in the frontend. The agent-server requires no changes — we re-use POST /api/conversations with a parent_conversation_id so the server already keeps the cross-link.

After · acp-error-codes.ts

// unchanged
export function getAcpErrorHeaderKey(code) { ... }

// new — gate for the banner's switch-action slot
export function canShowAcpProviderSwitch(
  conversation: AcpRecoveryConversationShape,
): boolean {
  if (!conversation) return false;
  const isAcp =
    !!conversation.acp_server ||
    conversation.agent_kind === "acp";
  if (!isAcp) return false;
  return conversation.execution_status
      !== ExecutionStatus.RUNNING;
}

⚠ Why acp_server, not agent_kind. SharedConversation (the type returned by useUserConversation) doesn't carry agent_kind; only the discriminated AppConversation does. The agent-server stamps acp_server from info.tags.acpserver onto every conversation, so it's the cross-endpoint-reliable ACP detector. agent_kind === "acp" remains as a fallback for endpoints that surface the discriminated agent payload but skip the tag.

+ added · src/hooks/mutation/use-switch-acp-provider.ts

Mutation that forks the active conversation

A react-query mutation that:

  1. Reads the source conversation's persisted metadata (workspace, repo, branch, workspace mode, enabled plugins) via getStoredConversationMetadata(sourceId).
  2. Builds a CreateConversationVariables payload that targets the chosen AgentProfileSummary while carrying over every carried-over field, plus parentConversationId so the agent server keeps the cross-link.
  3. Calls useCreateConversation().mutate; on success navigates to /conversations/{newId} via useNavigate().
  • Exports SWITCH_ACP_PROVIDER_MUTATION_KEY for useIsMutating guards from anywhere (including the banner).
  • useSwitchAcpProviderCallback(sourceId) returns a stable (profile) => void that no-ops while the mutation is pending — guards against double-clicks during the navigation round-trip.
  • Failure handling: failed creates raise the standard toast (displayErrorToast); we do NOT navigate on failure, so the user keeps the original conversation context.

Risks & follow-ups

  • Concurrency: double-clicking the menu item is harmless — the callback no-ops while isPending. No timing tests beyond the "stable identity" case have been added; a real reproduction would need an agent-server.
  • Cloud backends: the hook calls useCreateConversation which already branches on backend.kind === "cloud", so the fork should work for cloud backends without extra glue. Not yet exercised end-to-end.
  • Plugins carry-over: we pass the source's plugins array verbatim. If a future plugin has a conversation-local flag, that needs its own filter step.
  • Out of scope: no proactive "switch provider" button on healthy conversations — the user asked specifically for the recovery case. A future PR could surface the same flow from a new toolbar entry on finished / paused conversations.
